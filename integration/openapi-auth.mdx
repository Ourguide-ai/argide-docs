Every call the agent makes to your API carries the credentials you set under **Tools** → **Server Side** → **Authentication**. Pick a type, fill in its fields, and click **Save Configuration**.

## Auth types

| Type | Fields | Header Argide sends |
| --- | --- | --- |
| **None** | — | No auth header |
| **Bearer Token** | **Bearer Token** | `Authorization: Bearer <token>` |
| **API Key** | **API Key**, **API Key Header** (optional) | `X-API-Key: <key>`, or your header name |
| **JWT Forward** | — | `Authorization: Bearer <signed-in user's token>` |

<Note>
  Argide ignores `securitySchemes` and `security` in your spec. Authentication is configured only here, and it applies to every enabled endpoint.
</Note>

## Which one to use

| Your API… | Use |
| --- | --- |
| Doesn't require authentication | **None** |
| Accepts one service token for all requests | **Bearer Token** |
| Accepts one key in a custom header | **API Key** |
| Needs to know which end user is asking ("my orders", "my account") | **JWT Forward** |

<Warning>
  With **Bearer Token** or **API Key**, every user's requests go out with the same credential. The agent can reach anything that credential can — for any user who asks. Don't use a shared credential for endpoints that return per-user data; use **JWT Forward**.
</Warning>

## Bearer Token

Paste the token **only** into **Bearer Token** — for example `sk_live_abc123`, not `Bearer sk_live_abc123`. Argide adds the `Bearer ` prefix itself. There's no header-name field: the token always goes in `Authorization`.

## API Key

1. Paste the key into **API Key**.
2. Optionally set **API Key Header** to the header your API expects, such as `X-Acme-Key`. Leave it empty to use `X-API-Key`.

Argide sends the key as-is, with no prefix.

## Saved credentials

- Credentials are stored encrypted and never shown again. Once saved, the field shows "Credentials are already saved. Enter a value to replace them." Leave it empty to keep the saved value.
- **Bearer Token** and **API Key** need a credential the first time you save.
- Switching to **None** or **JWT Forward** deletes any saved credential.
- The agent can't override your auth header. If your spec declares a header parameter named `Authorization` or the same as your API key header, Argide drops the agent's value and sends yours.

## JWT Forward

JWT Forward lets the agent call your API as the signed-in user. Your backend mints a short-lived token for each user, the widget passes it to Argide, and Argide forwards that exact token to your API as `Authorization: Bearer <token>`.

Selecting **JWT Forward** has no fields — the token comes from the user's browser session. Setting up the token is covered in [Identity verification](/integration/identity-verification).

### What your API receives

| The user is… | What happens |
| --- | --- |
| Signed in, with a valid token | The request carries `Authorization: Bearer <token>`. |
| Anonymous, or never identified | The agent still has the tools, but the request goes out **without** an `Authorization` header. Your API should return `401`. |
| Signed in, but the token has expired | Argide doesn't send the request. It tells the agent the user's session expired, so the agent can ask them to sign in again. |
| Signed out with `resetAndPreserveSession` or `resetAndClearSession` | The token is revoked. Later requests go out without an `Authorization` header. |

### Verify the token in your API

Verify the signature with your `ARGIDE_AUTH_SECRET` and the `HS256` algorithm, then read the user ID from `sub`, `userId`, or `user_id` — whichever your backend put in the token.

<CodeGroup>

```javascript Node.js (Express)
const jwt = require('jsonwebtoken');

function requireArgideUser(req, res, next) {
  const [scheme, token] = (req.headers.authorization || '').split(' ');
  if (scheme !== 'Bearer' || !token) {
    return res.status(401).json({ error: 'Sign in required' });
  }
  try {
    const claims = jwt.verify(token, process.env.ARGIDE_AUTH_SECRET, {
      algorithms: ['HS256'],
    });
    req.userId = claims.sub || claims.userId || claims.user_id;
    next();
  } catch {
    res.status(401).json({ error: 'Invalid or expired token' });
  }
}

app.get('/my/orders', requireArgideUser, async (req, res) => {
  const orders = await db.orders.findMany({ where: { userId: req.userId } });
  res.json(orders);
});
```

```python Python (FastAPI)
import os

import jwt
from fastapi import Depends, Header, HTTPException


def argide_user_id(authorization: str = Header(default="")) -> str:
    scheme, _, token = authorization.partition(" ")
    if scheme != "Bearer" or not token:
        raise HTTPException(status_code=401, detail="Sign in required")
    try:
        claims = jwt.decode(
            token, os.environ["ARGIDE_AUTH_SECRET"], algorithms=["HS256"]
        )
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401, detail="Invalid or expired token")
    return claims.get("sub") or claims.get("userId") or claims["user_id"]


@app.get("/my/orders")
async def my_orders(user_id: str = Depends(argide_user_id)):
    return await db.orders.find_many(user_id=user_id)
```

</CodeGroup>

Return a clear `401` when the header is missing or the token is invalid. The agent sees the status and can tell the user to sign in.

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| `401` with **Bearer Token** | Paste the token without the `Bearer ` prefix. Argide adds it, so a pasted prefix is sent twice. |
| `401` with **API Key** | Check **API Key Header** matches the header your API reads. Empty means `X-API-Key`. |
| `401` with **JWT Forward** | The user isn't identified, or your API verifies with a different secret. See [Identity verification](/integration/identity-verification). |
| The agent says the user's session expired | The token's `exp` passed. Re-mint tokens before they expire. |
| Auth in your spec has no effect | Argide ignores `securitySchemes`. Configure auth on **Server Side**. |
